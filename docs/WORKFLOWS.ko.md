## 공통 운용

- 요청을 한두 문장으로 정리하고 이미 제공된 맥락·제약·결정을 먼저 반영한다.
- 사용자 지시와 호스트의 권한 규칙을 우선한다. 이미 허용된 작업에 확인을 반복하지 않는다.
- 결과가 달라지는 정보만 질문한다. 유용한 초안이 가능하면 가정을 표시하고 진행한다.
- 작은 작업에 워크숍·장문 계획·새 승인 단계·전체 개발 절차를 강제하지 않는다.
- 스킬의 원본 파일과 필요한 참조만 읽는다. 모든 프로필과 참조를 한꺼번에 로드하지 않는다.
- 증거로 확인한 내용, 추론, 미확인 사항을 구분한다. 실행·열람·청취하지 않은 결과를 검증했다고 쓰지 않는다.
- 생성 도구·계정·런타임이 없으면 제작 명세·프롬프트·검증 계획까지 준비하고 실제 제작은 미완료로 표시한다.
- 호스트에 실제 노출된 도구를 사용한다. Claude 전용 명령·훅을 Pi에서 실행 가능한 기능으로 간주하지 않는다.
- 스킬을 읽었다는 이유로 CLAUDE.md·훅을 추가하거나 외부 패키지·플러그인을 자동 설치하지 않는다.
- 새 외부 설치가 필요한 경우 기존 도구로 가능한 경로를 먼저 찾고, 설치는 현재 작업 범위와 호스트 권한에 따른다.
- 재사용한 자료의 출처·버전·사용 조건을 남기고, 알 수 없는 권리는 확인 필요로 표시한다.
- 완료 시 결과, 수행한 검증, 남은 한계를 간결하게 보고한다. 불필요한 형식 선택 질문으로 끝내지 않는다.

## requirements — 기능·비기능 요구사항

1. 사용자·업무 목표·현재 불편·기대 결과·사용 상황을 먼저 추출한다.
2. 기능 요구사항(FR), 비기능 요구사항(NFR), 업무 규칙, 제약, 가정, 제외 범위를 구분한다.
3. 사용자가 말한 구현 방안에서는 해결하려는 필요를 추출하되, 이미 결정된 방안을 임의로 번복하지 않는다.
4. 정상 흐름과 오류·취소·복구·권한 차이에서 필요한 행동을 확인한다.
5. NFR은 사용성·접근성·신뢰성·성능·운영성·보안 등 해당 업무에 필요한 품질만 도출한다.
6. 요구사항마다 출처와 상태를 남긴다. 출처 없는 추정은 확인된 요구사항으로 승격하지 않는다.
7. 합격 기준은 관찰 가능한 행동과 측정 조건으로 쓴다. 합의하지 않은 응답 시간·정확도·가용성 목표는 TBD로 둔다.
8. 충돌하는 요구는 각각의 출처와 영향을 제시한다. 충돌을 조용히 합치거나 임의로 해결하지 않는다.
9. 필요한 질문만 묶어서 하고, 얻은 정보로 우선순위와 수용 기준을 갱신한다.

권장 형식: `ID | FR/NFR | 요구사항 | 출처 | 확인됨/가정/TBD | 우선순위 | 수용 기준`.
수용 기준은 `Given 조건, When 행동/사건, Then 관찰 결과`로 작성한다.
짧은 요청에는 작은 표로 충분하다. 기술 스택·아키텍처 선정은 요청된 경우에 이어서 수행한다.

## game — 레퍼런스와 게임 제작

1. 장르·플레이 경험·타깃 기기·엔진·화면 크기·기존 스타일에서 작업의 경계를 정한다.
2. 관련 게임·에셋·UI·효과의 원본 레퍼런스를 찾고 실제 이미지·플레이 영상·음원을 확인한다.
3. 검색 설명이나 썸네일만 확인했다면 확인 범위를 표시한다. 플레이 영상을 봤다는 주장으로 확대하지 않는다.
4. 레퍼런스마다 `관찰 내용 | 채택할 요소 | 피할 요소 | 현재 게임에 맞는 이유`를 남긴다.
5. 대표 에셋이나 작은 장면을 먼저 제작해 스타일·비례·가독성을 확인한 뒤 같은 계열로 확장한다.
6. 에셋별 사용 위치·규격·투명도·피벗·애니메이션 상태·명명 규칙을 필요한 수준으로 정한다.
7. 실제 엔진에서 원래 표시 크기, 배경 대비, 움직임, 입력 반응, UI 상태를 확인한다.
8. 이펙트는 발동·타격·종료 시점과 판정의 일치, 전투 정보 가림, 목표 기기의 프레임 비용을 점검한다.
9. 사운드는 실제 재생으로 루프 연결·음량 균형·동시 발음·동작과의 타이밍을 확인한다.
10. 청취 수단이 없으면 파형 검사와 실제 청취를 구분하고 청취 검증을 미완료로 남긴다.
11. 수정은 발견된 품질 문제를 대상으로 한다. 정지 이미지 하나로 애니메이션 품질이나 게임 내 가독성을 확정하지 않는다.

산출물에는 실제 파일, 사용 위치, 레퍼런스 출처, 에셋 권리 상태, 확인한 엔진·기기 조건을 남긴다.
제작 도구가 없으면 에셋 목록·아트 방향·생성 명세를 전달하고 이미지·이펙트·음원을 생성했다고 쓰지 않는다.

밸런스 분석에서는 실제 규칙과 데이터로 모델을 만들고 보통 플레이·최적화 플레이·경계 조건을 비교한다.
시뮬레이션은 고정 시드와 반복 결과의 분포를 기록하며, 규칙 구현이 맞는지 확인한 뒤 수치를 조정한다.

## analysis — 원인과 해결책

1. 기대 결과와 관찰 결과의 차이, 발생 조건, 영향 범위를 정의한다.
2. 코드·로그·데이터·재현·사용자 보고에서 증거를 모으고 직접 관찰과 해석을 분리한다.
3. 데이터·제어·오류 흐름을 따라 최초로 기대와 달라지는 관찰 지점을 찾는다.
4. 원인을 하나로 고정하지 말고, 결정을 바꿀 수 있는 경쟁 가설을 최소한으로 세운다.
5. 가설마다 지지 증거·반대 증거·예측·기각 조건을 적는다.
6. 선행 가설을 구분하는 가장 저렴한 점검이나 실험을 실행하거나 제안한다.
7. 결과에 따라 가설을 기각·약화·유지한다. 그럴듯한 설명만으로 원인 확정을 선언하지 않는다.
8. 직접 원인, 촉발 조건, 기여 요인, 검출 실패, 복구 지연을 필요한 만큼 구분한다.
9. 제거·단순화·우회·수정·재설계·추가 관측 등 원인에 작용하는 해결책을 만든다.
10. 검증할 것은 원인 설명의 타당성과 개선 효과다. 현상 하나가 사라진 것을 전체 해결로 확대하지 않는다.

보고 순서: `결론/현재 가설 → 결정적 증거 → 대안 → 다음 점검 → 미확인 사항`.
5 Whys는 근거가 확보된 인과 관계를 요약하는 데 사용한다. 질문 횟수나 단일 원인을 강제하지 않는다.

## comparison — 대안 비교

1. 비교 목적, 선택 가능한 후보, 이미 확정된 제약을 정의한다. 의미가 있으면 현상 유지도 포함한다.
2. 예산·필수 기능·일정·호환성 같은 탈락 조건부터 적용한다.
3. 도입비와 반복 비용, 효과, 변경 범위, 유지보수, 운영 부담, 가역성을 비교한다.
4. 수치의 출처·버전·측정 조건·기간을 붙이고 추정치와 실제 측정치를 구분한다.
5. 근거가 부족하면 범위·정성 비교·TBD를 사용한다. 정밀한 점수와 가중치를 임의로 만들어 객관성을 연출하지 않는다.
6. 가중 비교가 필요하면 기준과 가중치의 근거를 먼저 밝힌다. 사용자 선호의 추정은 가정으로 표시한다.
7. 비용·성능·선호가 바뀔 때 순위가 뒤집히는 조건을 확인한다. 불확실한 입력이 결론을 지배하면 작은 검증을 우선한다.
8. 실행 가능한 기본안을 추천하고, 다른 안을 선택하게 되는 조건과 가장 중요한 미확인을 함께 제시한다.

하나의 조건으로 선택이 결정되면 복잡한 점수표를 만들지 않는다.

## vision — 비전 AI 분석

1. `촬영 → 라벨 → 전처리 → 모델 → 임계값 → 배포` 흐름에서 증상을 위치시킨다.
2. 카메라·조명·초점·노출·제품 위치·트리거·누락 프레임을 확인하고 모델 문제로 단정하지 않는다.
3. 라벨 정의·누락·불일치·모호한 결함을 실제 사례로 확인한다.
4. 분할 단위를 제품·개체·로트·시간·사이트에 맞춘다. 동일 제품의 다른 카메라·연속 프레임·유사 이미지가 분할을 넘는지 검사한다.
5. 검증 세트에서 임계값과 설정을 선택하고, 최종 평가용 held-out 세트는 잠근다. 평가 결과를 보고 반복 튜닝한 세트는 최종 독립 평가로 부르지 않는다.
6. 학습·평가·배포의 크기 조정, 채널 순서, 정규화, 후처리, 모델 버전을 비교한다.
7. 같은 데이터·평가 규칙에서 기준 모델과 후보를 비교한다. 전체 점수와 함께 FP/FN 사례를 본다.
8. 제품·카메라·조명·결함 종류·크기 등 중요한 구간별 오류를 분리하고 표본 수와 불확실성을 밝힌다.
9. 미탐과 오탐의 업무 비용에 따라 임계값을 검토한다. 정확도 목표나 허용 불량 유출률을 임의로 정하지 않는다.
10. 지연은 촬영·전송·대기·추론·후처리를 구분해 측정하고, 실제 기기·부하·백분위 조건을 남긴다.
11. 변경 요인을 가능한 한 분리해 비교한다. 데이터·조명·임계값 개선과 모델 교체의 비용·효과를 함께 평가한다.

실험 기록에는 데이터 버전·분할·설정·체크포인트·평가 조건을 남긴다. 데이터가 없으면 진단 계획까지를 결과로 보고한다.

## manufacturing — 제조업 SW 분석

1. 불량의 발생 원인과 검사·통제에서 놓친 원인을 분리한다.
2. 공정·작업 조건·센서·촬영·통신·SW 상태·판정·배출 동작의 경계를 그린다.
3. 품목·로트·라인·설비·시점·작업 조건을 연결해 발생 범위를 확인한다.
4. 타임스탬프와 제품 식별자로 트리거·프레임·검사 결과·배출 명령의 연결을 검증한다.
5. 누락·중복·지연·순서 바뀜·재시도·복구가 판정과 현물에 어떤 차이를 만드는지 확인한다.
6. 측정 방법과 기준의 일관성을 먼저 확인한다. 사용할 수 없는 공정능력 지표나 일률적인 샘플 수를 강제하지 않는다.
7. 임시 억제 조치와 영구 개선을 구분하고, 조치가 어떤 원인 또는 검출 실패에 작용하는지 설명한다.
8. 파일럿과 운영 관측으로 개선 효과를 확인한다. 물리 작업·고객 통지·승인을 수행했다고 꾸며 쓰지 않는다.

단일 장애에는 필요한 8D 요소만, 반복되는 공정 손실에는 적절한 측정·개선 절차를 적용한다.
GPU·모델 교체는 가능한 후보 중 하나다. 센서·소프트웨어·공정 변경을 같은 기준으로 비교한다.

## coding — 일반 코딩

1. Ponytail full을 기본 구현 태도로 삼아 요청을 완수하는 가장 작은 일관된 변경을 목표로 한다.
2. ECC search-first로 호출부·테스트·설정·기존 구현·설치된 의존성을 먼저 찾는다.
3. 외부 해법이 필요하면 공식 문서·기존 패키지·원본 구현을 조사하고 채택·확장·직접 구현을 비교한다.
4. Context7을 사용할 수 있으면 실제 설치 버전에 맞는 문서를 찾는다. 사용할 수 없으면 공식 문서와 로컬 코드를 확인한다.
5. 프로젝트의 기존 스택·관례를 존중하고 요청하지 않은 레이어·래퍼·옵션·의존성을 추가하지 않는다.
6. 변경이 영향을 주는 호출부·타입·설정·테스트까지 완수하고, 무관한 정리로 범위를 넓히지 않는다.
7. 원래 증상과 중요한 경계·실패 조건을 검증한다. 구현을 그대로 복제하는 테스트나 작은 변경마다 전체 TDD 절차를 강제하지 않는다.
8. 최종 변경 상태에서 의미 있는 검증을 수행한다. 린트·빌드·테스트 통과와 실제 요구 충족의 범위를 구분한다.
